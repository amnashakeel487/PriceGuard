# Requirements Document

## Introduction

PriceGuard is an automated e-commerce price tracker and alert system. This feature set introduces the public-facing
**Landing Page** and a complete **User Authentication flow** — Registration, Email Verification, and Login — on top of
the existing FastAPI + React 19/Vite stack. After a user is verified, the registered email address is reused
automatically to deliver price-drop alert notifications whenever a tracked product falls to or below the user's
configured budget.

The backend authentication infrastructure (UserManager, auth router, OTP-based verification via SMTP) already exists
in the codebase. This specification formalises the requirements for the frontend pages and the integration wiring that
connects those pages to the existing backend endpoints.

---

## Glossary

- **Landing_Page**: The public marketing page served at the application root (`/`) before a user is authenticated.
- **Auth_Flow**: The sequence of Registration → Email Verification → Login pages.
- **Registration_Form**: The UI form on the `/register` page where a new user provides email and password.
- **Verification_Form**: The UI form on the `/verify` page where a user enters the 6-digit OTP sent to their email.
- **Login_Form**: The UI form on the `/login` page where a verified user authenticates with email and password.
- **OTP**: A one-time 6-digit numeric passcode generated by the backend and delivered via SMTP email; valid for 15 minutes.
- **Session_Cookie**: The `pg_user` HTTP-only cookie set by the backend (`/api/auth/login` and `/api/auth/verify`) to persist authentication state across requests.
- **Auth_Guard**: A frontend route-protection component that redirects unauthenticated users to `/login` before allowing access to the protected dashboard.
- **Dashboard**: The existing `/`, `/products`, `/analytics`, `/alerts`, and `/settings` pages that require authentication.
- **Alert_Email**: A price-drop notification email sent to the user's registered and verified email address by AlertManager when a tracked product price falls to or below the user's target price.
- **API_Client**: The `src/api/client.js` module that handles all HTTP calls from the frontend to the FastAPI backend.
- **User**: A person who has submitted the Registration_Form; may be unverified or verified.
- **Verified_User**: A User whose OTP was accepted by the backend, setting `verified = true` in `data/users.json`.

## Requirements

### Requirement 1: Landing Page

**User Story:** As a visitor, I want to see a compelling marketing page that explains what PriceGuard does, so that I can understand the product and decide to sign up.

#### Acceptance Criteria

1. THE Landing_Page SHALL be accessible at the `/` path when no active Session_Cookie is present.
2. THE Landing_Page SHALL display the PriceGuard brand name, tagline, and a value proposition description of no more than 40 words covering automated price tracking and budget-based email alerts.
3. THE Landing_Page SHALL include a call-to-action button styled with the `btn-primary` class that is visible within the initial viewport (above the fold) and navigates the visitor to the `/register` path.
4. THE Landing_Page SHALL include a secondary link that navigates the visitor to the `/login` path.
5. THE Landing_Page SHALL render without horizontal overflow at viewport widths of 320 px, 768 px, and 1920 px; text SHALL remain legible (minimum 16 px body font); and interactive controls SHALL not overlap at any tested width.
6. THE Landing_Page SHALL use the existing design system tokens defined in `src/index.css` (CSS custom properties `--bg`, `--surface`, `--violet`, `--teal`, etc.) to maintain visual consistency with the Dashboard.
7. IF a Verified_User visits `/`, THEN THE Auth_Guard SHALL redirect the Verified_User to the `/dashboard` path instead of displaying the Landing_Page.

### Requirement 2: User Registration

**User Story:** As a visitor, I want to register with my email address and a password, so that I can create a PriceGuard account and start tracking product prices.

#### Acceptance Criteria

1. THE Registration_Form SHALL be accessible at the `/register` path.
2. THE Registration_Form SHALL contain an email input field and a password input field.
3. WHEN a visitor submits the Registration_Form with a non-empty email and a non-empty password, THE Registration_Form SHALL call `POST /api/auth/register` with the provided credentials.
4. WHEN the backend returns HTTP 200 from `POST /api/auth/register`, THE Registration_Form SHALL navigate the visitor to the `/verify` path, passing the submitted email address as route state for pre-population.
5. IF the backend returns HTTP 409 from `POST /api/auth/register`, THEN THE Registration_Form SHALL display the error message returned in the response `detail` field inline below the form.
6. IF the backend returns any HTTP error other than 409, or returns no HTTP response (network failure), from `POST /api/auth/register`, THEN THE Registration_Form SHALL display a generic error message: "Registration failed. Please try again."
7. WHILE a registration request is in-flight, THE Registration_Form SHALL disable the submit button AND display a visible loading indicator; each control MAY be toggled separately.
8. IF the visitor submits the Registration_Form with an empty email field or an empty password field, THEN THE Registration_Form SHALL display a validation message inline adjacent to each empty field without making a network request; email format validation beyond emptiness check SHALL NOT be performed client-side.
9. WHEN a Verified_User visits `/register`, THE Auth_Guard SHALL redirect the Verified_User to `/dashboard`.

### Requirement 3: Email Verification

**User Story:** As a newly registered user, I want to verify my email address with a one-time code, so that my account is activated and I can log in.

#### Acceptance Criteria

1. THE Verification_Form SHALL be accessible at the `/verify` path.
2. THE Verification_Form SHALL contain a numeric-only OTP input field accepting exactly 6 characters (max length 6) and a submit button.
3. WHEN the Verification_Form is navigated to from the Registration_Form, THE Verification_Form SHALL pre-populate the email display from the route state email value; that email SHALL also be used as the submission parameter in `POST /api/auth/verify`.
4. IF the Verification_Form is navigated to directly without route state email, THEN THE Verification_Form SHALL redirect the user to the `/register` path.
5. IF the user submits the Verification_Form with fewer than 6 characters or with non-numeric characters, THEN THE Verification_Form SHALL display a validation message inline and SHALL NOT make a network request.
6. WHEN a user submits the Verification_Form with a 6-digit OTP, THE Verification_Form SHALL call `POST /api/auth/verify` with the email and OTP.
7. WHEN the backend returns HTTP 200 from `POST /api/auth/verify`, THE Verification_Form SHALL navigate the user to `/dashboard` without displaying any error messages.
8. IF the backend returns HTTP 400 from `POST /api/auth/verify`, THEN THE Verification_Form SHALL display the error message from the `detail` field (e.g. "Incorrect verification code." or "Verification code expired.").
9. WHEN the "Resend code" control is activated, THE Verification_Form SHALL call `POST /api/auth/resend-otp` with the email.
10. WHEN `POST /api/auth/resend-otp` returns HTTP 200, THE Verification_Form SHALL display only the confirmation message "A new verification code has been sent to your email." and SHALL NOT display any error message.
11. IF `POST /api/auth/resend-otp` returns an HTTP error, THEN THE Verification_Form SHALL display the error message from the `detail` field.
12. WHILE a verification or resend request is in-flight, THE Verification_Form SHALL disable the submit button, disable the "Resend code" control, and display a visible loading indicator.

### Requirement 4: Login

**User Story:** As a verified user, I want to log in with my email and password, so that I can access the PriceGuard dashboard to manage my tracked products.

#### Acceptance Criteria

1. THE Login_Form SHALL be accessible at the `/login` path.
2. THE Login_Form SHALL contain an email input field, a password input field, and a submit button.
3. WHEN a user submits the Login_Form with a non-empty email and a non-empty password, THE Login_Form SHALL call `POST /api/auth/login` with the credentials.
4. WHEN the backend returns HTTP 200 from `POST /api/auth/login`, THE Login_Form SHALL navigate the user to `/dashboard`.
5. IF the backend returns HTTP 401 from `POST /api/auth/login`, THEN THE Login_Form SHALL display the error message from the `detail` field (e.g. "Incorrect password." or "Please verify your email before logging in.") and SHALL remain on the `/login` path.
6. IF the backend returns any HTTP error other than 401 from `POST /api/auth/login`, THEN THE Login_Form SHALL display a generic error message: "Login failed. Please try again." and SHALL remain on the `/login` path.
7. WHILE a login request is in-flight, THE Login_Form SHALL disable the submit button AND display a visible loading indicator.
8. IF the user submits the Login_Form with an empty email field or an empty password field, THEN THE Login_Form SHALL display a validation message inline adjacent to each empty field without making a network request.
9. THE Login_Form SHALL display a link that navigates to `/register` for users who do not have an account.
10. WHEN a Verified_User visits `/login`, THE Auth_Guard SHALL redirect the Verified_User to `/dashboard`.

### Requirement 5: Authentication State and Route Protection

**User Story:** As a verified user, I want the application to remember that I am logged in so that I do not have to authenticate on every visit, and as the application, I want to prevent unauthenticated access to the dashboard.

#### Acceptance Criteria

1. WHEN the application loads, THE Auth_Guard SHALL call `GET /api/auth/me` to determine whether the current Session_Cookie represents an authenticated Verified_User.
2. WHILE the `GET /api/auth/me` request is in-flight, THE Auth_Guard SHALL display a visible loading indicator rather than rendering protected or public routes.
3. IF `GET /api/auth/me` returns HTTP 401 or any non-200 response, THEN THE Auth_Guard SHALL treat the user as unauthenticated and redirect any access to protected Dashboard paths to `/login`.
4. WHEN `GET /api/auth/me` returns HTTP 200, THE Auth_Guard SHALL permit the user to access Dashboard paths and redirect any access to `/`, `/login`, and `/register` to `/dashboard`.
5. THE Auth_Guard SHALL expose the authenticated user's email address to all child components via React context.
6. THE Dashboard SHALL include a logout control that calls `POST /api/auth/logout`; WHILE the logout request is in-flight, THE logout control SHALL be disabled.
7. WHEN `POST /api/auth/logout` returns HTTP 200, THE Auth_Guard SHALL clear the local authentication context and redirect the user to `/login`.
8. IF `POST /api/auth/logout` returns a non-200 response, THEN THE Auth_Guard SHALL display an error message "Logout failed. Please try again." and SHALL NOT clear the local authentication context.

### Requirement 6: Alert Email Delivery to Registered User Email

**User Story:** As a verified user, I want price-drop alert emails to be sent to the email address I registered with, so that I am notified when a tracked product price meets my target budget.

#### Acceptance Criteria

1. WHEN a monitored product's `last_price` falls to or below the product's `target_price` AND the product's `alert_sent` flag is false AND the product's `user_email` field is non-empty, THE AlertManager SHALL send an Alert_Email to the `user_email` address, then set `alert_sent` to true; WHEN the product's `last_price` subsequently rises above `target_price`, THE AlertManager SHALL reset `alert_sent` to false.
2. THE Alert_Email SHALL include the product name, current price, target price, drop percentage calculated relative to the product's `highest_price`, and a direct link to the product URL.
3. WHEN a product is added via `POST /api/products` for an authenticated Verified_User, THE products route handler SHALL store the Verified_User's registered email address in the product's `user_email` field so that Alert_Email delivery targets that address.
4. THE Alert_Email SHALL be sent using four SMTP configuration values read from environment variables: sender address, sender password, SMTP server host, and SMTP server port.
5. IF the SMTP delivery attempt fails, THEN THE AlertManager SHALL log the failure and record a failed alert entry; the monitoring loop SHALL continue operating regardless of whether logging or recording individually succeeds or fails.
6. IF a product's `user_email` field is empty at alert-check time, THEN THE AlertManager SHALL record a failed alert entry without making any SMTP connection attempt.

### Requirement 7: API Client Auth Methods

**User Story:** As a frontend developer, I want the API client to expose typed auth methods, so that all auth-related HTTP calls follow the same pattern as existing product and monitor calls.

#### Acceptance Criteria

1. THE API_Client SHALL expose an `auth.register(email, password)` method that calls `POST /api/auth/register` and returns the parsed JSON response.
2. THE API_Client SHALL expose an `auth.verify(email, otp)` method that calls `POST /api/auth/verify`; the method SHALL include `credentials: "include"` in the request options to persist the Session_Cookie.
3. THE API_Client SHALL expose an `auth.resendOtp(email)` method that calls `POST /api/auth/resend-otp` with the `email` field in the request body.
4. THE API_Client SHALL expose an `auth.login(email, password)` method that calls `POST /api/auth/login` with `credentials: "include"` to persist the Session_Cookie.
5. THE API_Client SHALL expose an `auth.me()` method that calls `GET /api/auth/me` with `credentials: "include"` and returns the authenticated user object containing at minimum the user's email address and verified status.
6. THE API_Client SHALL expose an `auth.logout()` method that calls `POST /api/auth/logout` with `credentials: "include"`.
7. WHEN any auth endpoint returns a non-2xx HTTP status, THE API_Client SHALL throw an `ApiError` with the `detail` field from the response body as the error message; IF the response body does not contain a `detail` field, THEN the HTTP status text SHALL be used as the error message.
